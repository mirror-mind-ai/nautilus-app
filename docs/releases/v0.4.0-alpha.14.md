# v0.4.0-alpha.14 - One intent, a model per provider

**Date:** 2026-11-12

## Highlights

- **An intent holds a model per provider.** A Model Intent keeps one name and up to four models,
  one for each provider, each with its own thinking level. The name stands for the purpose; the
  models are how each provider serves it (CR256).
- **Choosing by name, or by provider.** The menu lists each purpose once. Choosing the name uses
  the first provider in your order whose model can run, so a provider that cannot run is skipped.
  When an intent has more than one model, its providers sit beside the name and each chooses its
  own. The footer still names the purpose, and the model it shows tells the provider (CR256).
- **Settings edits the models and the order.** The Model Intents panel lists every model under
  its name, composes an intent from one or more models ("Add a model from another provider"), and
  orders the providers once there is more than one (CR256).
- **A long intent name is no longer cut with the model behind it.** The 260px cap on the footer's
  model control is gone. The name is the only part that gives way, with an ellipsis, when the
  line lacks room; the model stays whole, and hovering the control shows the whole phrase (CR255).
- **Still Intel-only and unsigned on macOS;** the Windows bundle is unsigned.

## Where We Started

An intent was exactly one model and one thinking level, so the purpose and the model serving it
were one thing. Keeping a purpose on two providers took two intents with the provider written into
each name, the limit of twelve intents left no room for a third provider, and moving every purpose
to the other provider meant choosing a different intent each time. Separately, the footer's model
control was capped at 260px, so a long intent name filled it and hid the model.

## What Changed

- **The store.** The Model Intents file moves to schema 2.0.0: each intent has a name and a list of
  bindings, at most one per provider, and the file keeps the provider order. A file written before
  this release (1.0.0) is read as intents of one binding each, with nothing lost, in TypeScript and
  in the native validator, and is written back as 2.0.0 on the next save.
- **Recognition.** Conversations keep storing the concrete model and thinking level, as before. The
  footer names an intent when the configuration in force equals any of its bindings. Changing the
  provider order affects the next choice, not a conversation that already holds one.
- **The footer.** The intent's name is its own element inside the control; the control shrinks to
  the room its line has, and its title carries the intent and the exact model.

## What Does Not Change

The same Pi and the same `mirror-mind@0.44.0` core as alpha.13. No table in a home's database
changes, and the agent settings file is untouched.

## Conscious Exclusions

- **An older app cannot read a 2.0.0 file.** An installation before this release reads only 1.0.0,
  so an intents file already written in the new shape must be put back before going back a version.
  The first save in this release writes 2.0.0.
- **The intent itself is not stored in a conversation,** only the model it chose. Resolving the
  intent anew on each turn is a later step.
- **The provider order is global,** not per intent.
- **No signing or notarization,** on macOS or Windows, and **no Apple Silicon build.**

## What We Learned

Two things that move together look like one until a second provider arrives: the name of a purpose
and the model behind it had to be pulled apart before a purpose could outlive a provider. And a
limit written for one length of text becomes a bug at the next.

## Next Horizon

Storing the intent in a conversation and resolving it per turn, installing the Windows app and its
voice component from the published artifacts on a Windows machine, signing and notarization, and a
conversation held with a persona (CV-015's next design step).
